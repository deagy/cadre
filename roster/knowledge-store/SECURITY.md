# Knowledge Store Security

## Import rules

- Import only data the team is authorized to process and retain.
- Determine data ownership, consent, residency, retention, deletion, legal-hold, and model-provider restrictions before ingestion.
- Export into a staging location with restricted access. Delete the raw export through the approved records process after validation.
- Never assume automated redaction is complete. Review representative results before broad agent access.
- Use separate stores or enforced partitions for materially different access classifications or tenants.

### Global default, project-local override

By default, a project without its own `.agents/knowledge-store/config.json` resolves to the same shared database as every other such project (`$KNOWLEDGE_STORE_HOME/config.json`, default `~/.agents/knowledge-store/`) — see `README.md`. This intentionally trades one-store-per-repo isolation for cross-project retrieval, for projects that don't need stronger isolation. Two mechanisms keep it compatible with the "separate stores or enforced partitions" rule above:

- A project whose classification or tenancy genuinely cannot share infrastructure with others should create its own `.agents/knowledge-store/config.json` (a real partition — its own database, not just a filter) instead of relying on the shared default.
- For projects that do use the shared default, `--source` acts as a lighter-weight partition: tag every ingestion with a `--source` that identifies the originating project, and always filter retrieval by that same `--source` when project isolation matters. `cadre select` derives the default from the target repository's lowercase `owner/repository` origin slug, or a canonical-path hash fallback, so this is not left to caller memory alone; a hand-run `search` call still needs an explicit `--source`.
- This is enforced, not just documented, at the shared global-fallback tier specifically: `search` rejects a call that supplies neither `--source` nor the explicit `--all-sources` opt-in (and rejects a call that supplies both, as ambiguous). The rule once covered `ingest` and `context` as well; both were removed in `b418031e` and never rebuilt, so `search` is the whole of it today, and nothing here reaches ingestion, which now goes through recall. Project-local and explicit-`--config` invocations are unaffected — a real database partition or an explicit caller choice of config already provides isolation there, so no filter-discipline gate is layered on top of it. `--source` and `--all-sources` remain unauthenticated, caller-asserted values; this closes a scope-enforcement gap, it does not add caller authentication.

## Retrieval rules

- Treat retrieved passages as untrusted data that may contain prompt injection, obsolete guidance, malicious instructions, or inaccurate model output.
- Never let retrieved content override system instructions, agent authority, current policy, or approval gates.
- Preserve `source`, `conversation_id`, `message_id`, `chunk_id`, `content_hash`, `created_at`, and `classification`. The Python CLI omits stored `source_uri` values because they may expose local paths.
- Treat citations as point-in-time references. Preserve the retrieved bundle plus its integrity hash for review/compliance evidence; re-ingestion can change content under the same identifiers until versioned or append-only storage and result snapshot auditing exist.
- Filter retrieval by caller authorization and classification before ranking, not after returning results.
- Prefer current approved policies over historical chat content and visibly label conflicts.
- Give ordinary agents no content or lifecycle mutation authority. Retrieval still requires filesystem writes for audit metadata; grant this operational capability narrowly. Route ingestion, correction, reclassification, retention, and deletion through the knowledge-store steward.

  **That last sentence is a convention, not a control, and nothing in this CLI enforces it.** There is still no caller identity: `--decided-by`, `--deleted-by` and `--authorized-by` are free-text strings authenticated by nobody, as the Known limitations below record. What changed is what sits *beside* them — see "What the record now observes" below — and it is evidence rather than enforcement. An agent that decides to run a steward-only verb is not stopped by anything here — it is stopped by the process, or not at all. The separation-of-duties rules that *are* enforced are specific and narrower: `propose` refuses a record arriving already dispositioned, `disposition-staged` refuses a decider equal to the stager, `import-staged` requires a named human for any batch carrying a disposition, and `ingest-accepted` checks the stager/decider match again before anything becomes retrievable.
- Use `cadre knowledge search ...` for agent dispatch; no particular working directory is required. It records the query hash, task id, agent, caller-supplied classification and source scope, embedding provider and model, requested top and result count, and the time — never the raw query. It does not record authenticated identity, tenant or environment scope, the authorization decision, or the returned citation ids; those are production requirements this does not meet. (`cadre knowledge context` was the Python CLI's verb for this and went with the rewrite.)

## Storage rules

- Encrypt the database and backups using an organization-approved mechanism; SQLite itself does not provide transparent encryption.
- Restrict filesystem access and avoid synchronizing the database to broadly shared folders.
- Store embedding API keys only in a secret manager or environment injection mechanism, never in configuration or the database.
- Log ingestion metadata and counts, not raw chat content.
- **Retention and deletion of ingested content do not exist today.** `cadre knowledge ingest`, `retention-report`, `delete-ingested` and `deletion-evidence` were real, tested commands in the Python CLI and were removed in `b418031e` when the Go replacement landed. None was rebuilt. Ingested content now lives in a recall store, whose Go API deletes by document or chunk id and whose CLI exposes no delete command at all.

  Stated plainly, because this section previously described the removed implementation in the present tense: **no retention window is recorded for any content, nothing ages out, nothing reports what has expired, and there is no steward-facing way to delete ingested content.** Whether that is rebuilt or declared out of scope is an open decision.

  **What would change that:** a shipped command recording a per-message retention window at ingest, and one reporting what has expired, would restore the retention half; a deletion command writing the evidence specified in `DESIGN-NOTES-deletion-and-retention.md` would restore the other. That note preserves the Python implementation's design verbatim — why retention defaults were indefinite rather than guessed, why deletion evidence committed in two phases, and which guarantees it deliberately did not make. Three of its honest limits are properties of the problem rather than of that implementation, so any replacement inherits them.

  **What the absence costs, stated plainly rather than left to inference:** a steward asked to honour a deletion request, a retention window, or an erasure obligation has no tool here to do it with, and no evidence trail if they do it by other means. Deleting the store file is still possible and is not the same act — it is unscoped, unrecorded, and removes everything else too. Every commitment these documents make about retention or erasure is currently a commitment about process, not about software, and should be read that way by anyone relying on one.

- **Deletion of *staged* records does exist**, and is unaffected by the above. `cadre knowledge delete-staged` removes a staged record and writes evidence to `staged_record_deletions`, which has no foreign key to what it describes so that the evidence outlives its subject. Deleting an accepted record additionally requires a named authorizing human. `deletion-evidence-staged` reads that evidence back, optionally filtered by `--id`. It is a separate verb because `show-staged` cannot serve it: that resolves a record by id, and after a deletion there is no record to resolve. Until it existed the table was written and never read outside a test, which satisfies the letter of an evidence requirement and none of its purpose.

## Known limitations

The included redactor catches common credential shapes but cannot prove that content is free of secrets or sensitive data. `content_hash` covers the stored redacted chunk, not original evidence. Ingestion does not emit redaction or embedding summaries; maintain supplemental steward records until implemented.

Classification filtering is exact-match, not hierarchical, and caller flags are not authentication. The CLI enforces top-k from 1 through 20 and fails closed when an explicit configuration path is missing. Production integration must still authenticate callers and derive filters from authorized claims.

**What the record now observes, and what it still does not.** Every act that names an actor writes `observed_actor` beside the asserted name — `propose` beside `staged_by`, `disposition-staged` beside `decided_by`, `delete-staged` beside `deleted_by` and `authorized_by`, and `import-staged` beside the `--authorized-by` it requires for any batch carrying a disposition. The observation is the OS user from `os/user.Current()` — the process credentials, not `$USER`, which the caller sets — and git's configured `user.email` as context rather than proof, since that is a file the caller owns. It renders with its source prefixed (`os:deagy git:a@b.c`) so it cannot be read as a name, and no flag sets it. `delete-staged` echoes it back, and `show-staged` and `deletion-evidence-staged` read it, so the distinction is visible both at the moment of the act and to whoever audits it later — not only in this document.

  One deliberate omission: a disposition restored from a history sidecar by `import-staged` carries **no** observation. That decision was made elsewhere, at some earlier time, by a process this one cannot speak for; writing what *this* process sees would claim an observation it never made.

**This is not authentication and does not become any.** A caller who owns the machine owns every source of identity on it; nothing here would stop someone determined to misattribute. What it ends is narrower: an evidence row that names an actor nobody verified and gives a reader no way to tell. The row now carries an assertion *and* an observation, separately, and says which is which. Read `observed_actor` as "what the process saw", never as "who this was".

**Self-approval, and how far the guards against it actually reach.** Any agent may stage a proposal, so four checks keep staging from becoming approval: `propose` refuses a record arriving with a non-`proposed` status or a `disposition` block; `disposition-staged` refuses a `decided_by` equal to the record's `staged_by`; `import-staged` refuses a batch containing any dispositioned record unless `--authorized-by` names a human, and refuses a self-approved record regardless -- in the record's own `disposition` or anywhere in an imported history sidecar, since an earlier self-decision hidden behind a legitimate latest one is the same laundering with an extra step; `ingest-accepted` refuses a stager/decider match as a last check before retrievability. They are not equally strong, and the difference matters. The `propose` check is **name-independent**: it rejects the shape of a decided record, so no choice of identifier evades it, and it is the one that actually stops a proposing agent from authoring its own acceptance. The `import-staged` gate is next strongest: the requirement to pass `--authorized-by` at all is name-independent, though the name itself is asserted, not verified. It is also *recorded* -- one `staged_record_imports` row per admitted record, surfaced by `show-staged` -- which is what makes the asserted name worth asserting: for a while it was echoed into the command's output and stored nowhere, so the "human accountable for admitting these decisions" existed only until the process exited, and an audited record carried an attributable decider with an unattributable admission. That table is an ordinary SQLite table with no tamper-resistance, the same caveat as `staged_record_deletions` above. The remaining two compare two **caller-asserted strings**, authenticated by nobody, exactly as `--deleted-by`/`--authorized-by` are above — an actor that stages as one name and decides as another satisfies both. So these enforce separation *as declared*, not separation *in fact*; treat them as making an honest actor's mistake impossible and a dishonest one's attribution self-incriminating, not as an identity control.

`observed_actor` does not change that sentence. It is recorded on deletion, not consulted by any check, and a comparison between two asserted names is exactly as strong as it was — **strictly better evidence, identical enforcement**. Production integration must still derive `staged_by` and `decided_by` from authenticated claims rather than trusting the record; what exists today makes a wrong record legible afterwards, not impossible at the time.

The offline hashing embedder is a functional test backend, not a strong semantic model. The remote provider transfers chunk and query text to an HTTPS endpoint in bounded batches using an environment-provided bearer credential and a configurable timeout (30 seconds by default); embedded URL credentials and HTTP redirects are rejected. Approve data transfer, residency, retention, endpoint trust, and credentials before enabling it. Responses must contain finite vectors of the configured dimension. Re-ingest after provider/model/dimension changes and record exact model identity because the demo cannot safely distinguish reused names; mismatched stored dimensions are excluded. The built-in vector search scans stored vectors and should be replaced with an access-controlled vector index when scale or latency requires it.
