## Summary

A squash merge collapses a branch into a single commit with no merge parent. If
that branch contained a merge of some other branch `B`, git afterwards has no
record that `B` was ever merged: the merge-base does not advance, and every file
`B` contributed looks like an independent addition on both sides.

Observed concretely. A remediation branch merged `origin/main` so that six files
added by an earlier PR could be modified. That branch was then squash-merged into
its target. The target's merge-base with `main` stayed at the pre-merge commit,
and the next comparison reported **add/add conflicts on all six files plus a
seventh**, even though the target's content was a strict superset of `main`'s.
The pull request flipped to `DIRTY` within seconds of the squash merge.

The content was never in danger. The repair is to merge the source again and
resolve every conflict to the branch side, which restores the ancestry so
later comparisons are honest. But the conflict is pure noise generated by the
merge strategy, and it arrives at the worst moment -- immediately after a
successful merge, when attention has moved on.

## Reusable rule

Do not squash-merge a branch that contains a merge commit when the target will
later be compared against, or merged with, the branch that was merged in. Use an
ordinary merge or a rebase, either of which preserves what squash discards.

This matters most in a stacked-pull-request workflow, where a PR targets another
PR's branch rather than the default branch, and bringing the base branch current
mid-stack is routine. The tell is a PR going `DIRTY` right after an unrelated
merge succeeded, with conflicts in files nobody touched on both sides.

## Recommended Retrieval Use

Retrieve for release, build, and review agents performing merges, and for any
agent operating a stack of pull requests that target one another. Not
repository-specific -- this is a property of git's squash strategy.
