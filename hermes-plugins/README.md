# Hermes skills (Cadre roles as a Hermes skill tree)

`skills/cadre/` is the roster rendered for [Nous Research's Hermes
agent](https://hermes-agent.nousresearch.com/docs/): one skill per catalog
role under `<domain>/<role-id>/SKILL.md`, one per workflow playbook under
`workflow-<name>/`, and `cadre-orchestrator/`, which carries the route table,
team recipes, the full catalog, and a `references/` copy of the shared-policy
corpus so an installed tree is self-contained.

Everything under `skills/` is generated by `cadre port-hermes-skills` (Go,
`internal/generators/hermes_port.go`) from `roster/` in this checkout; do not
edit it. `internal/generators/hermes_port_test.go` fails the build when the
committed tree and a fresh port differ. Regenerate with:

```sh
./bin/cadre port-hermes-skills
```

## Installing

Hermes loads skills from `$HERMES_HOME/skills/` (`~/.hermes/skills/` by
default); `hermes skills install` takes one skill at a time, so a tree is
copied in. `install.sh --runner=hermes` does that and `--uninstall` reverses
it. By hand:

```sh
rm -rf ~/.hermes/skills/cadre
cp -r hermes-plugins/skills/cadre ~/.hermes/skills/cadre
hermes skills list | grep -c cadre      # 172
```

## How a role runs

A Hermes session loads `cadre-orchestrator` through `skill_view`, selects
roles with `cadre select` (the CLI `install.sh` also installs), and dispatches
each role through `delegate_task`, passing the role skill's contract
verbatim as the child's context together with the working directory the
child must `cd` to. Each role skill's "Hermes Dispatch" section says which
Hermes tools its cadre capability tier permits; the tier is advisory in
Hermes, which has no per-child tool policy, so a read-only role is read-only
because its contract says so and the orchestrator checks its result, not
because the runner refused a write.
